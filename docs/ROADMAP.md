# Vaultisor — план развития после 5.2.0

Принципы, которые не меняются:

- Хранилище не делает сетевых запросов. Новые каналы — только локальные.
- Каждая новая поверхность атаки выходит отдельной версией, с разделом угроз
  в `SECURITY.md` и fault-injection тестами для команд, меняющих состояние.
- Секрет не попадает в буфер обмена, на диск или в аргументы командной
  строки, если пользователь явно не выбрал это сам.

## 5.3 — секреты серверов и локальный мост

**Профиль сервера** — тип записи для инфраструктуры: хост, пользователь,
набор `KEY=VALUE`, ключ бэкапов и заметки. Заменяет отдельные файлы
`*.dpapi` в скриптах эксплуатации.

**Импорт и экспорт**
- `.env`: вставка блока `KEY=VALUE` или файл; каждая строка — отдельное
  секретное поле.
- KeePass (KDBX 4), Bitwarden (JSON без шифрования и зашифрованный).
- Экспорт `.env` — только через мост в процесс или в файл по capability.

**Ссылки на секреты** — `vaultisor://<база>/<запись>/<поле>`. Ссылку можно
держать в шаблоне `.env`, конфиге или скрипте: в ней нет значения.

**CLI `vaultisor`**
- `vaultisor read <ссылка>` — значение в stdout, для конвейера.
- `vaultisor run --env-file <шаблон> -- <команда>` — подставляет ссылки
  в переменные окружения дочернего процесса.
- `vaultisor inject -i <шаблон> [-o <файл>]` — подставляет ссылки в текст.

**Мост**
- Транспорт — named pipe с ACL текущего пользователя, без сети.
- Если приложение не запущено, CLI запускает его. Если хранилище
  заблокировано, запрос поднимает экран входа.
- Каждый запрос подтверждается в окне Vaultisor: кто просит (имя, путь
  и хэш процесса), какие записи, PIN или Hello.
- Необязательный грант: «разрешить этому процессу эти записи на N минут».
- Отдельный раздел угроз: подмена вызывающего процесса, перехват pipe,
  наследование окружения, утечка через `ps` и журналы.

**Журнал доступа** — локальный, под MAC: раскрытие, копирование, выдача
через мост, экспорт. Просмотр в настройках.

**Вход без PIN** — по FIDO2-ключу в режиме «ПИН токена + касание».
- Включается, когда привязан хотя бы один ключ «ПИН + касание» и
  восстановление по частям в состоянии «Настроено». Включение подтверждается
  последний раз PIN и касанием ключа.
- Обёртка мастер-ключа под PIN удаляется, а не скрывается: иначе остаётся
  более слабый путь входа.
- Подтверждение изменений безопасности — касание и ПИН токена вместо PIN.
- Hello в этом режиме выключается: к FIDO2 он ничего не добавляет.
- Последний ключ «ПИН + касание» нельзя отвязать, пока не задан PIN.
- Восстановление — по частям Шамира; после него пользователь привязывает
  ключ или задаёт PIN.
- Ключи «только касание» по-прежнему открывают хранилище сами — это
  осознанное упрощение, но режим без PIN на них не включается.

## 5.4 — идеи из StarVault / HashiCorp Vault

- **Версии полей с откатом** (как KV v2) — для любых полей, а не только
  для паролей.
- **Напоминания о ротации** по возрасту секрета («`JWT_SECRET` не менялся
  180 дней»).
- **SSH-агент** с подтверждением каждой подписи (named pipe
  `openssh-ssh-agent`).
- **SSH CA**: короткоживущие сертификаты (например, на час), сервер доверяет
  только CA (`TrustedUserCAKeys`).

## Дальний план (исследования с прототипом на железе)

- **PIN внутри TPM.** Защитить ключ Device Secret паролем (usage auth) так,
  чтобы PIN проверял сам чип и ограничивал перебор. Тогда код под той же
  учётной записью не получает Device Secret молча. Риски: блокировка TPM
  защитой от перебора, поведение на разных чипах — нужен стенд.
- **Аппаратный счётчик в TPM (NV).** Закрыл бы окно между commit базы и
  записью checkpoint'а и откат файлов целиком. Windows не даёт приложению
  заводить NV-индексы без прав владельца TPM, поэтому нужен прототип через TBS
  и решение, как поступать на устройствах без такой возможности.
