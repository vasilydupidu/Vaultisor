# Vaultisor — жизненный цикл разработки (SDLC)

Документ описывает, как в Vaultisor появляется, проверяется и выпускается код.
Это не декларация о намерениях: каждый пункт соответствует конкретной команде
или файлу в репозитории, и почти всё из перечисленного исполняется автоматически
в CI. Если пункт нельзя выполнить командой — он здесь не нужен.

Продукт: офлайновый Windows-менеджер секретов. Сетевой поверхности нет,
многопользовательского режима нет, серверной части нет. Отсюда весь перекос
модели в сторону локального злоумышленника, целостности метаданных и цепочки
поставки — а не в сторону аутентификации, rate-limit и защиты API.

Правило проектирования, из которого следует почти всё остальное: **любое
изменение формата данных, которое нельзя проверить криптографически, считается
дефектом**. Схема БД, формат бандла и набор полей, входящих в MAC, — это API, а
не деталь реализации.

### Изменение формата данных

До первого публичного релиза продукт **не поддерживает обратную совместимость**.
Схема БД одна (`META_SCHEMA_VERSION = 1`, `RECORDS_SCHEMA_VERSION = 1`), миграций
нет, база создаётся сразу в актуальном виде. Это сознательный выбор: код миграций
— это код, который почти никогда не выполняется и почти никогда не тестируется,
но при этом имеет полный доступ к ключам.

После первого публичного релиза правило меняется на противоположное: версия
схемы инкрементируется, миграция пишется вместе с тестом «старая база → новая
база → данные читаются», и старый путь удаляется только через полный
мажорный цикл.

## 2. Реализация

Границы, которые нельзя нарушать (проверяются ревью и тестами):

1. **Webview не имеет полномочий на файловую систему.** Любая операция с путём
   идёт через одноразовую capability, которую backend выдаёт только после
   собственного native-диалога (`state.file_grants`, `pending_recovery_saves`).
2. **Секреты не живут в `String`/`Vec<u8>` дольше необходимого.** Мастер-ключ —
   `MasterKey` (зашифрован в RAM в простое), производные — `Zeroizing`.
3. **Ошибки, уходящие в webview, редактируются.** `VaultError::System` и
   `Storage` отдают префикс без деталей; подробности идут только в лог.
4. **Ни один метаданный не остаётся вне MAC.** Добавление колонки в `vault_meta`
   обязано сопровождаться полем в `MacInputs` — иначе падает тест
   `every_field_changes_the_mac`.
5. **Мьютексы `parking_lot` не реентрантны.** Функция, берущая `AppState`, не
   вызывает другую функцию, берущую `AppState`. Конфиг читается через
   `read_config_at(data_dir, key)`, который состояния не касается.
6. **Фактор не регистрируется, пока не доказан делом.** Аппаратный фактор
   (Windows Hello, FIDO2) сохраняется только после настоящей церемонии входа
   этим же фактором. Заявление аутентификатора о своих возможностях —
   не доказательство: `bPrfEnabled` у FIDO2 и успешная регистрация Hello
   уже приводили к тому, что сохранённый фактор оказывался нерабочим, а
   хранилище — закрытым. Флаги протокола проверяются по подписанным
   authenticator data, а не по тому, что мы запросили.

## 3. Проверки перед мёржем

Всё перечисленное — блокирующее. Локально одной командой:

```bash
npm run lint && npm test && npm run build && cargo fmt --all -- --check && cargo clippy --workspace --all-targets --all-features -- -D warnings && cargo test --workspace --all-features -- --test-threads=2
```

| Гейт | Команда | Где в CI |
|------|---------|----------|
| Типы фронтенда | `npm run lint` (`tsc --noEmit`) | `ci.yml → frontend` |
| Тесты фронтенда | `npm test` (vitest) | `ci.yml → frontend` |
| Порог покрытия | `npm run test:coverage` | `vitest.config.ts` (per-glob thresholds) |
| Production-сборка фронтенда | `npm run build` | `ci.yml → frontend` |
| Форматирование Rust | `cargo fmt --all -- --check` | `ci.yml → backend` |
| Линт Rust (warnings = errors) | `cargo clippy … -D warnings` | `ci.yml → backend` |
| Тесты Rust | `cargo test --workspace --all-features` | `ci.yml → backend` |
| RUSTSEC | `cargo audit` | `ci.yml → backend` |
| SCA (advisories + лицензии + источники) | `cargo deny check advisories licenses sources` | `audit.yml` |
| SCA npm | `npm audit --audit-level=moderate` | `audit.yml` |
| Релизный бинарь собирается | `cargo build --release --locked -p vaultisor` | `ci.yml → backend` |

`--test-threads=2` не оптимизация, а требование: тесты крипты намеренно
memory-hard, и на раннере с большим числом ядер параллельный запуск упирается в
память.

### Что именно покрыто тестами

Покрытие измеряется по зонам, а не одним числом — UI-экраны и крипта требуют
разного (`vitest.config.ts`):

- `src/lib/**` — 65 %
- `src/screens/vault/**` — 90 %
- `src/components/ui/**` — 60 %

На стороне Rust порога нет; вместо него — обязательные инварианты, каждый со
своим тестом:

| Инвариант | Тест |
|-----------|------|
| Разметка единственного биндинга `webauthn.dll` совпадает с SDK, включая PRF-структуры | `windows_api::webauthn_layout::*` (5 тестов) |
| Каждое поле метаданных входит в MAC | `storage::integrity::tests::every_field_changes_the_mac` |
| Границы полей в MAC однозначны (нет склейки) | `storage::integrity::tests::field_boundaries_are_unambiguous` |
| Боевые параметры Argon2id остаются memory-hard | `crypto::kdf::tests::production_defaults_stay_memory_hard` |
| Санитизированный бэкап не содержит аппаратных факторов | `commands::backup::tests::sanitized_backup_is_self_consistent_after_fido_removal` |
| Без TPM короткий PIN не принимается | `auth::pin::tests::without_tpm_only_long_secrets_are_accepted` |
| Режим FIDO2-ключа не слабеет от соседства с touch-only | `commands::vault::lifecycle::fido2_policy_tests::pin_touch_key_is_not_weakened_by_a_touch_only_sibling` |
| Touch-only принимает оба исхода проверки | `commands::vault::lifecycle::fido2_policy_tests::touch_only_key_accepts_both_outcomes` |
| Словари ru/en согласованы и без осиротевших ключей | `src/locales/locales.test.ts` |
| IPC-аргументы идут в camelCase | `src/lib/api.test.ts` |
| Версия одинакова в трёх манифестах, changelog и таблица поддержки обновлены | `src/lib/release.test.ts` |
| Генератор распределяет символы равномерно (rejection sampling работает) | `src/lib/generateSecret.test.ts` |
| Оценка энтропии никогда не завышается | `src/lib/entropy.test.ts` |
| Выдача генератора не расшифровывается чужим blob'ом | `storage::records::generated::tests::blob_from_another_row_does_not_decrypt` |
| Список генератора не возвращает значения в webview | `storage::records::generated::tests::listing_never_returns_the_secret` |

## 4. Цепочка поставки (SCA)

| Источник риска | Контроль |
|----------------|----------|
| Rust-зависимости | `cargo audit` (RUSTSEC) + `cargo deny check advisories` |
| Лицензии | `cargo deny check licenses` — allowlist в `deny.toml`, продукт под GPL-3.0-only |
| Подмена источника | `cargo deny check sources` — `unknown-registry = "deny"` |
| npm-зависимости | `npm audit --audit-level=moderate` |
| Воспроизводимость | `Cargo.lock` и `package-lock.json` в репозитории, `npm ci`, cargo `--locked`, toolchain зафиксирован в `rust-toolchain.toml` |
| Нативная крипта | SQLCipher + OpenSSL 3.x собираются из исходников (`bundled-sqlcipher-vendored-openssl`), а не берутся из системы |
| Подмена wildcard-зависимости | `cargo deny check bans` — `wildcards = "deny"`, исключение только для path-зависимостей внутри workspace |
| Подмена git-зависимости | `cargo deny check sources` — `unknown-git = "deny"` |
| Подмена GitHub Action | все `uses:` закреплены по SHA коммита; обновление пина — вручную, с проверкой `zizmor` online |

Граф зависимостей в `deny.toml` зафиксирован на `x86_64-pc-windows-msvc`. Без
этого проверки идут по объединённому графу всех платформ и спотыкаются о GTK/glib,
которых в Windows-бинаре нет ни строкой.

### Запуск

Автоматических запусков нет: push, PR и расписание workflows не запускают.
Каждый workflow стартует только вручную:

```bash
gh workflow run ci.yml          # полный CI
gh workflow run audit.yml       # cargo-deny + npm audit
gh workflow run release.yml     # пробная релизная сборка без публикации
gh run watch
```

Настройки репозитория: Actions принимаются только закреплёнными по SHA
(`sha_pinning_required`), токен workflow по умолчанию только читает, запуск
из PR внешних участников ждёт одобрения. Ruleset запрещает удалять `main`
и переписывать его force-push'ем, а теги `v*` — удалять и переставлять.

Основная проверка — локальные гейты из раздела 3; `cargo deny` и `npm audit`
стоит прогонять перед каждым релизом и после обновления зависимостей.

### Почему Actions закреплены по SHA

`uses: actions/checkout@v5` указывает на тег **чужого** репозитория. Тег —
движущаяся ссылка: его владелец, или тот, кто получит доступ к его аккаунту,
может перенаправить её на другой коммит. Этот код исполняется в нашем CI с
доступом к `GITHUB_TOKEN`. Владение собственным репозиторием от этого не
защищает никак.

Атака не гипотетическая: в марте 2025 через компрометацию
`tj-actions/changed-files` все теги были переставлены на вредоносный коммит, и
секреты утекли из тысяч репозиториев. SHA переставить нельзя — в этом и смысл.

Цена пина — ручное обновление: новый SHA берётся из релиза action, версия
пишется комментарием, а `GH_TOKEN=$(gh auth token) zizmor --persona pedantic
.github/workflows` проверяет, что SHA принадлежит этому action и совпадает с
версией в комментарии.

## 5. Релиз

1. Поднять версию в трёх файлах: `package.json`, `src-tauri/Cargo.toml`,
   `src-tauri/tauri.conf.json`. Синхронизировать локфайлы (`cargo update -w`,
   `npm i --package-lock-only`).
2. Обновить таблицу поддерживаемых версий в `SECURITY.md` и changelog в `README.md`.
   Пропустить молча нельзя: `src/lib/release.test.ts` сверяет версию во всех
   трёх манифестах с обоими документами. Пункт дважды пропускался, пока был
   только строчкой в этом файле.
3. Прогнать полный набор гейтов из раздела 3.
4. Собрать портативный бинарь: `.\build.ps1` → `release\Vaultisor-<версия>.exe`.
   Имя всегда несёт версию: безымянная копия рядом провоцирует запустить не ту
   сборку и прислать лог не от неё.
5. Проверить workflows: `actionlint` и `zizmor --persona pedantic .github/workflows`.
6. Коммит + аннотированный тег `vX.Y.Z`, пуш тега. Тег сам ничего не
   запускает.
7. Включить Actions и запустить релиз вручную:
   `gh workflow run release.yml --ref vX.Y.Z -f publish=true`. `build` собирает
   `.exe` один раз и выкладывает артефакт, `publish` проверяет его хэш и
   публикует `Vaultisor-<версия>.exe`, `SHA256SUMS.txt` и `build-info.json`.
   После прогона Actions снова выключить (раздел 4, «Запуск»).

### Устройство релизного pipeline

`.github/workflows/release.yml`, запускается только вручную. Без
`publish=true` это пробная сборка: проверки и артефакт, без релиза.
`publish=true` допустим только с тега, совпадающего с версией в `package.json`:

```text
checks (ci.yml без кэша) → build → [attest] → publish
```

| Job | Права токена | Что делает |
|-----|--------------|------------|
| `checks` | `contents: read` | полный CI; кэш сборки отключён, чтобы кэш из другой ветки не попал в релиз |
| `build` | `contents: read` | при запуске с тега сверяет его с версией, `npm ci`, toolchain из `rust-toolchain.toml`, `build.ps1` (cargo `--locked`), `SHA256SUMS.txt` и `build-info.json`; выкладывает их неизменяемым артефактом run'а |
| `attest` | `id-token: write`, `attestations: write` | provenance-attestation бинарника (Sigstore), выполняется при `publish=true`. Без неё `publish` не запускается |
| `publish` | `contents: write` | только при `publish=true`; ничего не собирает: скачивает тот же артефакт, проверяет `sha256sum --check`, создаёт релиз через `gh release create --verify-tag` |

Общие правила всех workflows: `permissions: {}` на уровне файла и явный минимум
на каждый job; `actions/checkout` с `persist-credentials: false`; `npm ci`
вместо `npm install`; кэш npm выключен (`package-manager-cache: false`);
значения `${{ github.* }}` попадают в скрипты только через `env`, не
подстановкой в текст команды.

Локальная проверка workflows перед коммитом:

```bash
actionlint
zizmor --persona pedantic .github/workflows
```

`zizmor` с токеном `gh` (`GH_TOKEN=$(gh auth token) zizmor …`) дополнительно
проверяет, что закреплённые SHA действительно принадлежат указанным actions
и совпадают с версией в комментарии.

Подробности — [`docs/RELEASE.md`](./RELEASE.md).

### Версионирование

SemVer, где «публичный API» — это **формат данных и IPC-поверхность**, а не
исходный код:

- **major** — меняется схема БД или формат бандла без пути миграции, удаляются
  IPC-команды, меняется форма их аргументов или ответа;
- **minor** — новая функциональность, обратно совместимая по данным;
- **patch** — исправления, не трогающие форматы.

Изменение состава полей, входящих в `meta_mac`, — всегда major: старая база с
новым бинарём не пройдёт проверку целостности.

Исключение действует, пока продукт не выпущен для внешних пользователей:
несовместимые изменения формата идут минорной версией без миграций (так
выпускаются версии 5.x). С первого публичного релиза правило выше обязательно.

## 6. Эксплуатация и реагирование

Приложение офлайновое, телеметрии нет, поэтому обратная связь приходит только
через GitHub. Приём сообщений об уязвимостях и сроки — в
[`SECURITY.md`](../SECURITY.md).

Локальные сигналы, на которые продукт реагирует сам:

- расхождение `meta_mac` → отказ открыть хранилище, а не «починка»;
- откат метаданных (внешний DPAPI-чекпойнт в `%LOCALAPPDATA%`)
  → отказ, требуется явное восстановление;
- откат баз записей или паролей сайтов (ревизии в том же чекпойнте)
  → `DATA_ROLLBACK`, продолжить можно только явным решением с проверкой PIN;
- серия неверных PIN → нарастающая задержка (30 с … 1 ч), без безвозвратной
  блокировки;
- смена сессии Windows, сон, завершение работы → блокировка хранилища.

## 7. Что осознанно НЕ делается

Честный список — чтобы он не выглядел как недоработка:

- **Нет Authenticode-подписи.** Бинарь публикуется unsigned, проверка — по
  SHA-256. Сертификат стоит денег и требует HSM; до появления такового
  подписывать нечем.
- **Нет автоматического CI.** Push, PR и расписание ничего не запускают.
  Гейты прогоняются локально, а CI,
  audit и релиз — вручную (раздел 4, «Запуск»). Dependabot не подключён:
  обновления зависимостей и пинов Actions — явное ручное решение.
- **Нет автообновления.** Апдейтер — это сетевой канал с правом записи в
  исполняемый файл; для офлайнового хранилища секретов это худший размен из
  возможных.
- **Нет защиты от вредоносного кода в сессии пользователя.** Если злоумышленник
  уже исполняет код под той же учётной записью Windows, он дождётся разблокировки.
  DPAPI, TPM и `CryptProtectMemory` повышают цену атаки, но не отменяют её.
- **Нет постквантовой криптографии.** `ml-kem` был удалён: гибридная обёртка не
  давала выигрыша против локального злоумышленника, а добавляла неаудированную
  зависимость в путь получения ключа.
